# 分割英文点検エージェント プロンプト雛形

置換変数: {{RULES}} 執筆規則ファイル / {{NOTATION}} 記法規則 / {{LEDGER}} 記号台帳(無ければ「なし」) / {{TEX}} 対象 tex / {{FROM}} {{LINES}} 範囲 / {{OUT}} 出力ファイル / {{TERMS}} 承認済み用語列挙 / {{ROUND_NOTE}} ラウンド注記(第2ラウンド以降は「修正済み本文なので残る欠陥は少ないはず。確信のある欠陥のみ」)。

---

数学論文の英語点検タスク。編集はせず、指摘のみをファイルに書く。

## 手順
1. {{RULES}} と {{NOTATION}} を全文読む(点検基準)。{{LEDGER}} があれば読む。
2. {{TEX}} の {{FROM}}行目から{{LINES}}行を Read(offset={{FROM}}, limit={{LINES}})で読む。
3. 英文の欠陥を指摘: 代名詞の先行詞曖昧、修飾句の係り先、語順、長すぎる主語(動詞まで8語超。仮主語・受動態・we 主語で短くする案を出す)、動詞選択、while/whereas、冠詞、言い換え(elegant variation)、単複、前置詞、主張の射程、目的語欠落、時制、comma splice、証明の中で記号で書ける関係を言葉で述べている文({{RULES}} 1.12。案は式に書き直した行全文。名前の無い対象に記号を与えるなら定義文を添え「自律執筆」と書く)。
3b. 証明の根拠の欠落を指摘: `proof-rigor.md`(プラグインの `rules/`)§1・§2・§4・§5 に反する段。非自明な結論を `Clearly` / `By construction` / `A direct computation shows` 等だけで済ませている、既知の定理を名前だけで引き適用条件を確かめていない、計算の中間式が無く再現できない、など。**案には置換文を書かず、欠けているもの(仮定・補題・計算・適用条件のどれか)を式で特定する**。説明文を足す案は出さない(同 §7)。
4. 記法の欠陥も指摘: {{LEDGER}} と不一致な記号、台帳に無い記号(台帳への追加を提案)、{{NOTATION}} の 1--6 への違反(アクセントの不一致、存在理由の無い添字、添字の順序、予約文字の衝突、明示形の繰り返し、マクロの混在)。
5. **記号の依存関係を全数確認する。**台帳の記号と本文の主要記号について、`\begin{document}` 以降の初出行を機械的に求め、定義行と突き合わせる。判定は 正順 / display 先行 / 前方参照 / 二重定義 / 未定義。display の中で先に現れ直後の `where` で定義される形は正順。行き先を明示した前方参照も正順だが、**明示しているのが別の対象なら前方参照に数える**。同じ文字が2つの意味を持つ組も、この突き合わせで拾う。
6. 指摘しないもの: 数学的内容、一文一行の改行位置、承認済み用語({{TERMS}})、台帳に載っていて {{NOTATION}} に反しない記号の選択、定理環境の構成、TeX コメント。
7. {{ROUND_NOTE}} 確信のない指摘は出さない(偽陽性はコストが高い)。

手順5は分割読みでは完結しない。**担当チャンクの外にある定義行を見落とすので、初出と定義の突き合わせはチャンク単位ではなく全文で1回行う**(オーケストレータが担当するか、専用の1エージェントを立てる)。

**記号は手で選ばず、本文から機械的に全数抽出する。**台帳と「主要な記号」から手で列挙すると、記号として意識していない文字が表に載らず、突き合わせの対象にすらならない。抽出は `\mathcal{X}` 系・`\widetilde{X}` 系・`\macro`・`X_` の4パターンを拾い、構造マクロと標準の数体系・群・演算子を除き、添字を落として基底記号に正規化する。2回以上現れるものを対象にすれば、局所的な一度きりの表現は落ちる。

**`tools/symbol_depgraph.py <tex>` がこの突き合わせを行う。**自分で書くなら次の2点を外さないこと。どちらも初版で間違えて誤った判定を出した(2026-08-22)。

- **複数行にまたがる display の内側も数式として扱う。**インライン `\(...\)` だけを行単位で拾うと、display で初出する記号の初出行が後ろにずれる(\(\cK_0\) が L2388 ではなく L2528 と出た)。`\[`・`equation`・`align`・`aligned`・`array`・`cases`・`bmatrix`・`split` の入れ子を深さで追う。
- **定義の合図は記号の直前(40文字以内)に限る。**行のどこかに `define` や `let` があるだけで定義行とみなすと偽陽性だらけになる(\(\cN\) の定義候補が6行出た)。合図には存在量化型(`there is`・`the existence of`)も入れる。これが無いと `the existence of a linear functional \(\bh\) with ...` を定義と認識できず、「定義が890行先にある」と誤報する。

出力は候補である。走る添字(\(i,j,k,a\))は「定義される記号」ではないので、単独文字の行は目視で落とす。残ったものを**本文と照合してから**報告する。

## 出力
{{OUT}} に Write で書く。形式:

```
## 裁定表
状態は 未処理 / 対応済(コミット) / 棄却 / 保留。適用のたびに同じコミットで更新する。

| 件 | 状態 | 内容 | 判断 |
| --- | --- | --- | --- |
| F1 | 未処理 | <1行で> | |

## F<番号> L<行番号> — 未処理
現: <その行の全文をそのまま>
問題: <1行で>
案: <置換後の行全文。\ref/\eqref/\cite/数式は一切落とさない。長すぎる場合は2文に分割し2行で>
```

指摘には通し番号 `F<n>` を振り、裁定表と見出しの両方に状態を書く。適用時に**両方**を更新する(`PLAYBOOK.md` 報告書の状態欄)。

**裁定表は先頭に1つだけ置く。**あとから別の切り口(記号の全数突き合わせ、規範との照合など)で指摘を足すときも、行は先頭の裁定表へ入れ、節のほうは散文で書く。表を分けると `tools/review_status.py` が2つ目を読まず、そこに書いた指摘が丸ごと集計から落ちる。2026-08-22 に71件の報告書が58件と数えられた。

指摘ゼロなら `CLEAN` とだけ書く。論文ファイルを編集しない。最終応答は「<件数>件を <ファイル名> に出力」の1行でよい。
