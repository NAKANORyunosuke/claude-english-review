# 数学英語の点検と修正

このスキルは**規則の実体を持たない**。すべてプラグインルート直下のファイルにあるので、
作業を始める前に該当ファイルを Read ツールで全文読み込むこと(要約や記憶に頼らない)。
パスはこの SKILL.md から見て2つ上がプラグインルートである。

## 1文でも英文を書く・直すとき

必ず読む。

- `../../rules/english-writing-rules.md`
  — 誤り型カタログ。§1 の12型(代名詞の先行詞、修飾句の係り先、語の距離、動詞選択、
  対比の while、冠詞、一物一名、単複、前置詞、主張の射程、長い主語、言葉で運ぶ証明)と、
  §3 の手続き規則11項(完全な文で出力する、節を落とさない、分割後に先行詞を数え直す、
  受け取った置換文もその場で点検する、など)。
- `../../rules/notation-rules.md`
  — 記法の設計と点検。アクセント、添字、予約文字、マクロの統一、記号台帳の運用。
  記号は序文で決まり本文へ波及するので、英文点検より先に確定する。
- `../../rules/terminology-rules.md`
  — 造語防止。技術的な複合名詞句を書く前に通す4段階の関門と、禁止パターン7型
  (名詞積み、一物多名、メタファーの術語化、定義済み形容詞の適用範囲逸脱、
  引用結果への命名、圧縮逆参照の名前化、ad hoc ハイフン連結)。
  **承認済み用語の一覧と banned リストはプロジェクト側にある**ので、そちらも見る。

規範の実体はすべてプラグイン側にある。**プロジェクト固有のものを規範へ書き足さない。**
書き足すとその原稿でしか通じない記述が規範に混ざり、他のプロジェクトはコピーして持つほかなくなり、
コピーは更新されなくなる。固有のものは config の次のキーから読む。

- `local_rules` — その原稿の点検で新しく出た誤り型、派生物の扱い、体裁の規約(一文一行など)。
- `local_terms` — 承認済み用語の一覧、出典を明示して輸入した語、その原稿固有の語感。
- `audit` / `build` — 自己検査のコマンド。`english-writing-rules.md` の §4 はここを見ろとしか書いていない。

新規に書く・翻訳するときは `../../rules/writing-guide.md`(声と時制、文の骨格、構成、
禁止事項)も読む。定型表現は `../../rules/phrasebook.md`。
**優先順位はプロジェクト規約 > writing-guide > phrasebook。**

### プロジェクト規約が規範原本を指しているなら、要約より先に原本を読む

`writing-guide.md` は規範原本(`EnglishBible` の `mathematical-writing.md` と
`matsumoto-style-guide.md`)の**要約**であり、そのことは同ファイルの冒頭に書いてある。
プロジェクト規約が原本を「規範本体」と定めているなら、**点検を始める前に原本を全文読む**。

要約だけで回すと**談話構造の層が丸ごと落ちる**。2026-08-22 の実測では、要約で59件を出した
あとに原本を当てて4件が追加で出た。ピボット句 `In this paper, we ...` の欠落、`Fact` 環境を
使わず同じ結果を3回インラインで引いていること、Abstract の文数と主語、subsection 冒頭の
目的宣言の不統一。いずれも要約には項目が無い。

一方で原本の機械層(評価形容詞・ヘッジ・読者管理修辞・文頭 Clearly・誤り表16行・
ロードマップ句)は要約でも拾える。**原本を読む価値は禁止語ではなく談話構造にある。**

原本は `EnglishBible` リポジトリのほか、`english-bible` プラグインの中にも入っている
(`~/.claude/plugins/cache/english-bible/english-bible/<version>/`)。プロジェクト規約が
書く作業ツリーのパスが解決しない環境でも、そちらから読める。

## 全文点検を回すとき

上に加えて `../../PLAYBOOK.md` を読む。フェーズ0(序文と記号の確定)から順に、
裁定基準、収束条件、コミット規約、報告書と引き継ぎ資料の書き方までを定める。

適用は手で行わず `../../tools/` を使う。

| ツール | 用途 |
| --- | --- |
| `apply_fixes.py` | 採用指摘の一括適用(旧文面の平坦一致アンカー、dry-run/apply) |
| `apply_renames.py` | **記号の改名**を JSON の指示書どおりに当てる。事前のヒット数アサート、上付き添字の破損検出、範囲内の旧トークン残存の確認まで |
| `symbol_depgraph.py` | **記号の全数抽出**と初出/定義の突き合わせ(未定義・前方参照・二重定義)。フェーズ B の中核 |
| `coinage_scan.py` | 造語候補スキャン |
| `glossary.py` | 技術的名詞句の全数抽出と分類 |
| `ledger_gate.py` | 記号を変えたのに台帳を直していないコミットを止める |
| `review_status.py` | 報告書の裁定表を横断集計し、引き継ぎ資料を生成する |
| `depgraph.py` | 依存グラフと番号系列の点検 |
| `finding_db.py` | **指摘の位置を保つ**。行番号は腐るのでアンカー(原稿の実文)を正とし、編集ごとのシフト・ハッシュ不一致時の引き直し・git 履歴からの復旧の3層で追う |
| `structure_db.py` | **各行が何をしている行か**を分類し、環境グループとページ・節を持たせる。定理環境の中の定義や命令文(台帳の決定3)をそこから拾う |
| `findings_push.py` | 指摘を集計サーバ(PostgreSQL)へ送る。**プロジェクトを横断した問いだけ**に使う。1リポジトリの状態は `findings.json` を見る |

**記号を触るときは `apply_renames.py` を使う。**手で置換スクリプトを書くと毎回同じ事故を起こす。
2026-08-22 の1回で、期待ヒット数のアサートが4回、実害を止めた。

**適用ツールには `--db <findings.json>` を付ける。**書き込みの直後に指摘の位置が直る。
`apply_fixes.py` は verify(行数が変わるので引き直す。消失は「片づいた」の意)、
`apply_renames.py` は retext(行数は変わらない。アンカーの文面を改名に追随させる)。
詳しくは `../../PLAYBOOK.md` の「指摘の位置は適用ツールに追わせる」。

## 収束の判定

英文の機械検査がゼロでも終わりではない。**プリアンブルのマクロ、記号の全数抽出、
`depgraph.py`、節冒頭の並び**は分割読みの視野の外にあり、英文が収束したあとから
出てくる。PLAYBOOK フェーズ B を別に回すこと。
